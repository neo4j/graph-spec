# ADR-0004: Port sequencing

Status: Proposed

## Context

The rebased branch (ADR-0002) holds both trees: the graph spec 4.0.0
implementation — Kotlin Multiplatform model under
`src/commonMain/kotlin/model/`, kotlinx-serialization codecs under
`codec/`, the SchemaMap-based legacy migration chain under `migrate/`,
the validator framework under `validate/`, the jsMain `@JsExport`
surface plus build-logic `TypeScriptModifierTask` codegen, the Go
module under `go/` (types generated by schemancer from `go/spec.json`,
itself generated from the Kotlin model by the Gradle
`generateGraphModelJsonSchema` task; validation/migration bridged into
Kotlin/Native via `src/bridge/`), and the five Kotlin/Go CI workflows
under `.github/workflows/` — alongside the v1 ontology overlay
(`ontology-spec.schema.json`, `docs/`, `examples/`, `scripts/`,
`.github/workflows/validate.yaml`).

ADR-0006 (Accepted) fixed the port's architecture: keep main's
machinery, re-targeted at the v1 schema; consumer-visible deltas are
limited to exactly two — the name (graph-spec → ontology-spec) and the
extensions area (ADR-0005). ADR-0003 fixed the schema's provenance:
hand-maintained, implementations conform, derivation arrow is schema →
language types, never model → schema; `TypeScriptModifierTask` and
`GenerateGraphModelJsonSchema.kt` have no v1 consumer. ADR-0002 set
the API-stability constraint those decisions are weighed against and
deferred the naming mechanics and this sequencing to ADR-0004.

What remains open, and what this ADR decides:

1. **Track order.** Six port tracks: (1) the Kotlin v1 model, (2)
   codecs and validators, (3) the 4.0.0 → 1.0.0 converter replacing
   the legacy `migrate/` chain, (4) TypeScript types, (5) Go bindings,
   (6) the Kotlin/Go CI workflows (`pr-guard-*.yaml`,
   `validate-*.yaml`, `release.yaml`). What blocks what?
2. **Naming mechanics and timing.** "graph-spec becomes ontology-spec"
   is sanctioned (ADR-0006), but the mechanical content per surface —
   Gradle modules/settings, Kotlin package names, the npm artifact,
   the Go module path — and when in the sequence the rename lands are
   undecided, and must be weighed against ADR-0002's API-stability
   constraint.
3. **Fate of the 4.0.0 model classes during the transition:**
   quarantine (move aside), replace-in-place, or delete-after-port.

Facts from the tree that constrain the answer:

- The Kotlin packages are top-level (`model`, `codec`, `migrate`,
  `validate`, `bridge`) with no `graphspec` segment; the only
  Kotlin-API-visible occurrences of the old name are the entry-point
  class `GraphSpec` / `GraphSpecConfig`, the `Type.GRAPH_SPEC` token,
  and build/artifact strings.
- The Gradle build is single-module: `settings.gradle.kts` sets
  `rootProject.name = "graph-spec"`; `build.gradle.kts` sets Maven
  coordinates `org.neo4j.importer:graph-spec` (publishing currently
  disabled via `if: false` in `release.yaml`), the npm packageJson
  name `@neo4j-importer/graph-spec`, and the Kotlin/Native shared-lib
  `baseName = "graphdatamodel"`.
- The Go module path is `github.com/neo4j/graph-spec/go/v4`; Go
  consumers also see `GRAPHDATAMODEL_LIB_PATH`, the
  `graphspec_noembed` build tag, and `libgraphdatamodel.{so,dylib}`.
- The legacy migration machinery already operates on the codec's
  `SchemaMap` tree (`MigrationPath.migrate(schema: SchemaMap, ...)`),
  not on model classes; the Kotlin/Native bridge's `migrate` export
  does the same.
- jsMain compiles in the same `./gradlew check` as commonMain: an
  in-place model rewrite breaks the jsMain `@JsExport` wrappers in the
  same commit. The Go module builds in its own workflow; the Gradle
  build never compiles Go.
- The Node `validate.yaml` workflow guards the schema/examples and is
  unaffected by the port; it stays active throughout.

## Decision

### Track order

**1 → Kotlin v1 model · 2 → codecs and validators · 3 → 4.0.0 → 1.0.0
converter · 4 → TypeScript types · 5 → Go bindings · 6 → Kotlin/Go CI
workflows.**

As an ordered list:
`["kotlin-v1-model", "codecs-and-validators", "converter-4.0.0-to-1.0.0", "typescript-types", "go-bindings", "kotlin-go-ci-workflows"]`

Dependency reasoning:

- **Track 1 (Kotlin v1 model) first.** Every other track compiles
  against or bridges into the model: codecs serialize it, validators
  walk it, the converter targets it, jsMain wraps it, the Go
  Kotlin/Native bridge exports functions over it. Its input is the
  hand-maintained schema (ADR-0003), which already exists. The model
  is re-targeted to the v1 format: id-keyed `nodes`/`relationships`
  maps, `label` / `labels.identifier`, type tokens
  (`STRING`, `LIST<STRING>`, `VECTOR<FLOAT>` + `dimension`), endpoint
  cardinality `count` / `min_count` / `max_count`, `tools`, and the
  named + `custom` extensions envelope.
- **Track 2 (codecs and validators) second.** The JSON/YAML formats
  and the `validate/` framework are model consumers, so they follow
  the model; the converter (track 3) reuses the codec `SchemaMap`
  layer and the format encode/decode pair, and the consumer surfaces
  (tracks 4–5) expose `validate()`, so they need the re-pointed
  validators. ADR-0003's conformance tests (SDK fixtures validated
  against `ontology-spec.schema.json`, round-trips reproducing
  schema-valid documents) land here on the Kotlin side.
- **Track 3 (converter) third.** The one-way 4.0.0 → 1.0.0 converter
  replaces the legacy `migrate/` chain. It needs the v1 model as its
  target and the re-pointed codecs as its read/write path, so it
  cannot precede tracks 1–2; the Go migration bridge (track 5) calls
  into it, so it precedes track 5. It is built the way the existing
  machinery already works: decode the 4.0.0 document to a `SchemaMap`,
  transform map → map, encode as v1 — it never needs the 4.0.0 model
  classes (see "Fate of the 4.0.0 model classes" below).
- **Track 4 (TypeScript types) fourth.** The jsMain `@JsExport`
  surface is compiled by the same `./gradlew check` that tracks 1–3
  keep green, so its real re-targeting — plus ADR-0003's retirement of
  the build-logic `TypeScriptModifierTask` codegen in favour of
  authored/schema-generated types — lands while the Kotlin build
  context is warm and needs no new CI machinery. The npm artifact
  rename lands in this track (below).
- **Track 5 (Go bindings) fifth.** Go has no hard dependency on track
  4, but it re-points an independent pipeline: schemancer now consumes
  `ontology-spec.schema.json` directly (ADR-0003's schema → types
  arrow), which kills the Gradle `generateGraphModelJsonSchema` task,
  `src/jvmMain/kotlin/schema/GenerateGraphModelJsonSchema.kt`,
  `go/spec.json`, and the `kotlinx-schema-generator` dependency; and
  its validation/migration methods bridge into Kotlin/Native, so it
  must follow tracks 1–3. Sequencing it after track 4 lets its
  generation drift-check land once, against the final
  schema-consuming pipeline.
- **Track 6 (Kotlin/Go CI workflows) last.** Guards validate what
  exists: re-pointing them before the code lands breaks every PR or
  guts the checks. Each track updates the slice of CI its own change
  needs to stay green; track 6 is the consolidation — re-pointing
  `validate-go.yaml`'s drift check at the new pipeline, updating
  `release.yaml`'s npm artifact name and tag lines, retiring the
  4.0.0-only task references, and re-activating the full
  guard/release matrix against the ported tree. The first release
  after track 6 opens the ontology-spec 1.0.0 line (`release/v1.0.0`,
  `go/v1.0.0` tags).

Keep-green rule: every track lands with `./gradlew check` and
`npm run validate` green. A track that breaks a dependent source set
carries the *mechanical* adaptation needed to keep it compiling
(track 1 carries the jsMain/bridge keep-compiling edits); the real
re-targeting of each surface belongs to its owning track.

### Naming: mechanics per surface and timing

The rename is sanctioned as one of the two consumer-visible deltas
(ADR-0006); weighed against ADR-0002's API-stability constraint, it is
deliberately minimal — artifact and entry-point names change, every
already-neutral name (packages, model classes) stays. **The rename
lands per-track, with each surface's own track**, so the consumer-visible
name delta lands exactly once per artifact, together with that
artifact's v1 port, and no separate rename PR re-touches files the
port just wrote.

Mechanically, per surface:

- **Gradle modules/settings (track 1).** `settings.gradle.kts`:
  `rootProject.name` `graph-spec` → `ontology-spec` (single-module
  build; no submodule renames). `build.gradle.kts`: Maven coordinates
  artifactId `graph-spec` → `ontology-spec` (group `org.neo4j.importer`
  unchanged; Maven publishing is disabled in `release.yaml` and stays
  so), POM `name`/`description`/`url` updated, Kotlin/Native
  `baseName` `graphdatamodel` → `ontologymodel`.
- **Kotlin package names (track 1).** Unchanged: the packages are
  top-level `model`, `codec`, `migrate` → converter, `validate`,
  `bridge` and carry no `graph-spec` segment. The only Kotlin-API-visible
  renames are the entry point `GraphSpec` → `OntologySpec` (with
  `GraphSpecConfig` → `OntologySpecConfig` and the
  `Type.GRAPH_SPEC` token following), which is part of the sanctioned
  name delta, and the native-lib names above. Everything else about
  the Kotlin API is covered by ADR-0002/ADR-0006 API stability.
- **npm artifact (track 4).** `@neo4j-importer/graph-spec` →
  `@neo4j-importer/ontology-spec` in `build.gradle.kts`' `packageJson`
  block; the generated `graph-spec.d.mts` filename follows the root
  project name; `release.yaml`'s publish step is mechanically
  unchanged. The `repository` URL stays `github.com/neo4j/graph-spec`
  until the GitHub repo rename, which is out of scope for this
  workstream (ADR-0002: the endgame is local; remote operations are
  excluded) and remains an open core-group decision (ADR-0001).
- **Go module path (track 5).** `github.com/neo4j/graph-spec/go/v4` →
  `github.com/neo4j/graph-spec/go`: the `/v4` major-version suffix
  belongs to graph spec 4.x and Go modules carry no suffix at v1, so
  the suffix is dropped for the ontology-spec 1.x line; the repo
  component stays `github.com/neo4j/graph-spec` until the GitHub repo
  rename (out of scope, as above), after which the path becomes
  `github.com/neo4j/ontology-spec/go`. The Go-visible native names
  follow the rename in the same track: `GRAPHDATAMODEL_LIB_PATH` →
  `ONTOLOGYMODEL_LIB_PATH`, build tag `graphspec_noembed` →
  `ontologyspec_noembed`, `libgraphdatamodel.*` → `libontologymodel.*`
  — all part of the sanctioned name delta, documented in
  `go/README.md` in the same change.

### Fate of the 4.0.0 model classes: replace-in-place

**Replace-in-place, track by track.** The v1 model is written into the
existing files and packages — `model/node/Node.kt` keeps its path; its
content is re-targeted — so git history shows the port as a diff and
there is never a second model in the tree (ADR-0006 rejected
dual-model maintenance; this avoids even a time-boxed one). 4.0.0-only
classes with no v1 counterpart are deleted in the track that obsoletes
them: the core `source`/`mapping`/`display` classes when their
extension-surface successors land per ADR-0005, the legacy `migrate/`
chain in track 3, the pretty/internal duality (`Internal.kt`,
`Pretty.kt`) with the model that no longer needs it, and
`GenerateGraphModelJsonSchema.kt` + `go/spec.json` in track 5. The
converter needs no kept 4.0.0 classes: it parses 4.0.0 documents
through the codec `SchemaMap` layer — the exact pattern
`MigrationPath` already uses — with checked-in 4.0.0 JSON/YAML
documents as test fixtures. The frozen tag `graph-spec-4.0.0`
(ADR-0001) remains the full, checkable-out reference for the old code.

## Alternatives considered

1. **Big-bang port: all six tracks in one change.** Rejected:
   unreviewable diff, no green intermediate states, and it violates
   the repo's same-change discipline (each change lands prose, schema,
   example, and now code, green) — a single flag-day PR cannot be
   bisected when something breaks.
2. **Converter first (migration story before the SDK).** Rejected:
   the converter's target is the v1 model and its read/write path is
   the re-pointed codecs; building it first means building against a
   nonexistent target, or keeping the 4.0.0 model as the converter's
   authority and inverting ADR-0003's schema-first rule.
3. **Consumer surfaces (Go bindings, TypeScript types) before the
   converter.** Rejected: both surfaces expose migration — the Go
   module's `migration` package bridges into the Kotlin/Native
   `migrate` export, and the `GraphSpec` entry API wires the
   `MigrationPath` — so landing them before track 3 either cements the
   legacy 4.0.0 migration chain into the v1 surface or ships consumer
   surfaces with migration stubbed out, and both are consumer-visible
   deltas beyond the two ADR-0006 allows.
4. **Parallel v1 tree alongside 4.0.0, then a switchover.** Rejected:
   it keeps two models in the tree for the entire port — the
   arrangement ADR-0006 rejected, time-boxed but with the same review
   and confusion cost — and because the in-place file and package
   names are occupied, the parallel tree is forced into temporary
   names that need a second, rename-only pass at switchover.
5. **Rename first: one rename PR before track 1.** Rejected: it
   publishes the new name over 4.0.0 content (an "ontology-spec"
   artifact that is graph-spec inside is a lie to consumers), breaks
   `go get` for existing consumers by dropping `/v4` while the module
   still serves 4.0.0, and serialises every port track behind a
   change that delivers no v1 function.
6. **Rename last: one rename PR after track 5.** Rejected: the
   artifact names are deliverables of their own tracks — a v1 Go
   module under the `/v4` path and a v1 npm package under the old
   name publish the new format as if it were the old product — and a
   final rename pass re-touches every build file the port just wrote,
   doubling review churn for no stability gain.
7. **Quarantine the 4.0.0 classes: move them to a legacy
   package/module, keep them compiling for the transition.**
   Rejected: it ships dead code in the published artifacts, duplicates
   the model in-tree for the whole transition, and buys nothing — the
   SchemaMap-based converter never needs the classes, and the frozen
   `graph-spec-4.0.0` tag is a better reference than a quarantined
   copy that must be kept compiling.
8. **Delete-after-port: leave 4.0.0 untouched until all v1 tracks
   land, then delete.** Rejected: since the in-place files are
   occupied, it forces the parallel-tree arrangement of alternative 4
   with all its costs, keeps the legacy migration chain authoritative
   until the very end, and makes the final deletion PR unreviewably
   large.
9. **CI re-pointed first (guards before the port).** Rejected: guards
   validate what exists — pointed at v1 expectations they fail on the
   unported tree, and weakened to pass they lose their value exactly
   when the riskiest changes land; `release.yaml` re-pointed early
   would publish half-ported artifacts under the new name.

## Consequences

- The port tracks are charted in the decided order; each track's
  change keeps `./gradlew check` and `npm run validate` green, with
  mechanical keep-compiling adaptations owned by the track that breaks
  compilation and real re-targeting owned by the surface's track.
- ADR-0003's conformance tests land with track 2 (Kotlin side) and
  track 5 (Go fixtures validated against `ontology-spec.schema.json`);
  a schema/bindings mismatch fails CI and the schema wins.
- Track 3 deletes the legacy `migrate/` chain; the converter is
  SchemaMap-based like today's `MigrationPath`, with 4.0.0 documents
  carried as test fixtures, so no 4.0.0 model class survives the port.
- Track 4 retires `TypeScriptModifierTask` /
  `TypeScriptModifierPlugin` / `script/TypeScript{Types,Unions}.kt`
  from the v1 path per ADR-0003; they are deleted with the last 4.0.0
  build files.
- Track 5 deletes `GenerateGraphModelJsonSchema.kt`, the
  `generateGraphModelJsonSchema` Gradle task, `go/spec.json`, and the
  `kotlinx-schema-generator` dependency; `generate-go-models.sh` runs
  schemancer against `ontology-spec.schema.json` directly.
- The consumer-visible name delta lands exactly once per artifact,
  with that artifact's v1 port: Gradle/Maven/native-lib names in
  track 1, the `GraphSpec` → `OntologySpec` entry point in track 1,
  the npm artifact in track 4, the Go module path and Go-visible
  native names in track 5, workflow and release names in track 6.
- The GitHub repo rename stays out of scope (ADR-0002); the Go module
  path's repo component and the npm `repository` URL follow it when it
  lands, and this ADR's Go module path decision
  (`github.com/neo4j/graph-spec/go`, no `/vN` suffix at v1) already
  fixes everything else.
- ADR-0005 (extension packaging) plugs into track 1's extensions
  envelope and decides what replaces the core `source`/`mapping`/
  `display` classes; until it lands, track 1 keeps those classes
  compiling with minimal adaptation.
- The Node `validate.yaml` workflow is untouched and guards the
  schema/examples throughout the port.
